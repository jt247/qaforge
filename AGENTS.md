# Shared agent operating instructions
Read README.md, standards/testing-standard.md, standards/security-testing-policy.md, standards/agent-collaboration.md, and the product QA guide before testing. Codex also reads CODEX.md; Claude Code also reads CLAUDE.md.

## Mandatory gate before any run
Every testing session starts with the agent stating, in chat: the goal (what is being tested and why), and what is required before testing can start (the templates/session-brief.md fields: URL and environment, build, requirements source, priority workflows, roles, whether account creation is authorized, messaging/payment sandbox scope, stop conditions and budget). Present this as a short plan. Do not run `configure`, `preflight`, `new-run`, or any browser action until the user gives an explicit confirmation of that plan in chat. `new-run` requires `--goal` and `--confirmed-by` and refuses without them; use the exact goal and confirmer name from the chat confirmation, never inferred ones.
Every confirmed session is logged with a date automatically: `new-run` appends one line to the product's `coordination/session-log.md` (timestamp, agent, run id, environment, confirmed by, goal), on top of the dated `manifest.json`, dated results, and `report.md` the run already produces. Do not keep a separate untracked log; this file is the record.
`new-run` also copies the run plan and session brief templates into the run as `plan.md` and `brief.md`, prefilled with the goal, confirmer, and lead agent. Fill the remaining fields of both from the confirmed chat brief before running `smoke`. The chat is not the record; these two files are.

## First run in a fresh clone
If `local/identity.json` is missing or `tooling/lab.py init` has never been run here, run `python3 tooling/lab.py init` before anything else. It checks Python and Git, reports whether ECC and a browser MCP are available, creates `local/identity.json` from the template, and runs `validate` plus the unit tests. Report its output to the user and stop if it says anything is missing.

## Browser testing protocol
Browser work is done through a browser MCP tool, never by guessing from HTML. Preferred: the `chrome-devtools` MCP that ECC ships as its default connector. Fallback: the Playwright MCP. If neither is available, stop and tell the user; do not mark browser cases as passed or failed without one.
Evidence lives in the run's `evidence/` directory (ignored by Git) and is named `<CASE-ID>-<step>-<UTC timestamp>.<ext>`, for example `AUTH-001-02-20260923T101500Z.png`. Every passed or failed result cites at least one evidence file through `result --evidence`. A screenshot must show the state the note asserts (the URL bar, the relevant control, the message, the data), not an unrelated page. Save console errors and the relevant network request or response as text when they support a finding; redact tokens and personal data first.
Use a fresh browser profile per run and per agent. Do not reuse a session that another run or the other agent is using.

## End of session checklist
Before you stop, in this order: record every case you touched (`result`), regenerate the report (`report`), update the product's `coordination/state.md` (latest run per agent, open findings by severity, blocked cases, next step), update `coordination/handoff.md` (what remains, fixture state, anything the other agent must know), update `findings/INDEX.md` if you raised or retested a finding, then `close` the run if it is complete or `release` the claim if you are handing off mid-run. A session that ends without these is incomplete.

The filesystem is durable context. Never infer completed tests from previous chat prose. Never report a pass without execution and evidence. Never invent product requirements, accounts, URLs, integrations, or backend coverage.
Use tooling/lab.py for configuration checks, run creation, results, and reports. Configuration records who authorized the assessment and how, and it expires after fourteen days. Claim a run with the CLI before browser testing; release it at handoff. Use separate run IDs and test accounts for parallel agents. Do not edit another agent's original evidence or results. Review through peer-review.md and the protocol in standards/agent-collaboration.md.
The two agents work inside the ECC engineering layer (github.com/affaan-m/ECC, MIT). Plan before changing lab tooling, run a fresh-context code review of every tooling change, and run a secret scan against the repository before enabling a new product target. README.md lists the exact ECC surfaces used.
Only target the explicitly enabled environment in product.json. Production defaults to read-only. Creating accounts, sending messages, changing records, or making payments needs that action allowed in the saved environment scope. Do not follow unexpected redirects outside approved hosts.
Keep credentials, OTPs, session states, test phone numbers, and unredacted personal data out of tracked files and reports. Evidence directories are ignored by Git. Redact before sharing.
Record blocked and not-run checks honestly. Freeze completed runs; fixes require a new linked run. Do not claim release readiness from reachability checks alone. No automatic deployment, notification to third parties, or risk acceptance.
